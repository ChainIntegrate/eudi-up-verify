## 1. Executive summary

The team fixed almost everything raised on 14 October, quickly and with care: every fix carries the finding ID in its commit, comes with regression tests (backend tests went from 63 to **105**, contract tests from 25 to **28**, all passing), and the remaining risks are written down in `docs/audit/README.md`. I re-ran the first audit's proof-of-concept tests on the new code:

- **UCL-01 (minting stalls after one failed transaction): fixed.** A reverting call is now caught by a simulation (`SIMULATION_REVERTED`) and the next valid mint goes through; open mints survive restarts (`mints` table + `reconcileMints`) and the monitor alerts on stuck mints and queues.
- **UCL-02 (countdowns abort the CIE step): fixed.** After 5 min 10 s the CIE step is still shown, and the success page survives the 15-minute mark (Chromium, fake clock).
- **UCL-05 (re-entrant `renounce()` during mint): fixed** in the redeployed contract (`nonReentrant`, event before mint); a re-entering "UP" now makes the simulation fail cleanly. The residual (a purpose-built fake Key Manager still passes the UP check) is documented and now harmless to the queue.
- **Dependencies:** the contracts tree went from 775 packages and 61 advisories to 255 packages and **0** advisories; backend and spike still 0.
- **Live site:** every static file served (14 files: HTML, JS, CSS, images, badge metadata) is **byte-identical** to commit `64ec68d`; security headers (CSP, HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy, nosniff) are present on every route, `/api/health` answers 404 from outside, `/metadata/*` has open CORS as intended, `server_tokens` is off.

What is still open or new:

1. **UCL-31 (Medium, new):** data-subject requests (`data:export` / `data:erase`) are executed on the word of whoever writes in with a UP address. There is no check that the requester controls that UP, so a stranger could obtain the list of **all** UPs of a person, or have their data erased and badges invalidated.
2. **UCL-34 (Low, new, from the UCL-03 fix):** the badge expiry is rounded **up** to the first day of the next month, so a badge stays valid up to ~31 days after the card has expired, while the pages say it "expires with the card". Rounding **down** (first day of the expiry month) discloses exactly the same (the month) and never outlives the card.
3. **Admin page (new):** solid design (owner-only login by ERC-1271 signature, HttpOnly/SameSite=Strict cookie, the server never holds owner keys). Two weaker points: anyone can block admin logins by filling the 1 000-challenge cache (UCL-32), and the documented emergency procedure restores the attester through the same server it assumes compromised (UCL-33).
4. **Hygiene:** the public repository publishes the server IP, SSH user and mail provider, and links the operator's UP to his real CIE (UCL-36); the certificate reference is kept after a renunciation/revocation longer than the notice says (UCL-35); a real `.p7m` is copied to world-readable `/tmp` during setup (UCL-37).
5. **Still open from the first audit, by decision:** UCL-08 separate signing/HMAC process (deferred to mainnet), UCL-13 CIE certificate policy (CP/CPS) for a private relying party, UCL-14 privacy notice completeness, UCL-25 off-site backups.

## 3. New findings

### UCL-31 — Data-subject requests are not authenticated (Medium)

**Where:** `backend/src/subject.js`, `backend/scripts/data-subject.js`, `docs/operations.md` §4, privacy notice §7 ("scrivendo ai contatti del punto 2 con l'indirizzo della UP").

**What happens.** The notice tells people to write to `info@chainintegrate.it` (or Telegram, or a GitHub issue) **with the UP address**, and the operator runs `data-subject.js export|erase --up 0x…`. Nothing in the procedure checks that the requester controls that UP. Because the person is found through the link of that UP:

- `export` returns **every UP linked to the same person** (primary, additional, migrated), their statuses and dates, exception tickets and statements. Sending it to the wrong requester discloses exactly the link between a person's UPs that the design tries to hide (and an Art. 15 response to the wrong person is itself a personal-data breach).
- `erase` invalidates all the person's valid badges on-chain and deletes their uniqueness key: a stranger could knock out someone's verified UPs with one e-mail.

UP addresses are public (they are shared via `/verifica/<up>` by design), so the only "secret" in the request is not a secret at all.

**Recommendation.** Before executing a request, ask the requester to prove control of the UP: e.g. sign a one-time text (`up-cie-link data request v1`, request type, UP, nonce, date) with the UP and check it with the existing `isValidUpSignature` (a small `--signature` option in `data-subject.js`, or an endpoint behind the admin page). Alternatively, let the holder do it themselves from "Il mio bollino" (signed request). Reply only to the channel the request came from, never send the export to a third address, and record the verification in the audit log. Say in the notice that a signature from the UP will be requested (Art. 12(6) GDPR allows asking for information needed to confirm identity).

### UCL-32 — Admin login can be blocked by filling the challenge cache (Low)

**Where:** `backend/src/admin.js:78-88` (`createChallenge`), router limiter 60 requests/min per client.

**What happens.** `POST /api/admin/challenge` is unauthenticated and accepts the owner address, which is public (`/api/config` → contract → `owner()`). Each call stores a challenge for 5 minutes; above 1 000 stored challenges every new one is refused with 429. With the per-client limit (60/min) and nginx's 10 r/s, four IPv4 addresses (or four IPv6 /64s) are enough to keep the cache full and lock the real owner out of the admin page. Each call also costs an RPC call (`owner()`). Impact is limited (the owner can still act from the UP directly or with the scripts), hence Low.

**Recommendation.** Do not keep server-side state for unauthenticated callers: make the challenge stateless (HMAC-signed text with an expiry, verified on login) and keep only a short "used nonce" list after a successful login; or cap at a few outstanding challenges per UP and evict the oldest instead of refusing new ones. Cache `owner()` for a minute.

### UCL-33 — Emergency "restore attester" relies on the server the procedure assumes compromised (Low)

**Where:** `docs/operations.md` §4 ("Emergenza (chiave dell'attestatore o server compromessi)"), `admin.js` `buildTx("restoreAttester")`, frontend `admin.js`.

**What happens.** Step 3 restores the attester from the admin page, which encodes `setAttester(minterAddress)` with the address **reported by the server**, inside JavaScript **served by the same server**. If the server was compromised (the scenario of this procedure), an attacker who still controls it can make the page propose their own key; the owner sees only the confirmation prompt generated by that page and the raw calldata in the wallet.

**Recommendation.** In the emergency procedure, after re-installing the server from a clean state, verify the new attester address independently (from the offline record written when the key was generated) against the calldata shown by the UP extension before signing; or build the `setAttester` calldata from the PC (a small script in `contracts/scripts/`) and send it from the owner UP. Stopping minting from the page (`setAttester(0)`) is safe as it is.

### UCL-34 — Badge expiry rounded up: the badge outlives the card by up to a month (Low)

**Where:** `backend/src/mints.js:106-108` (`badgeExpiry`), home page text ("Il bollino scade con la carta"), monitor/revocation checks on links with `expires_at > now`.

**What happens.** `badgeExpiry(notAfter)` returns the first day of the month **after** the card expiry (example: card expiring 14 Feb 2034 → badge valid until 1 Mar 2034). For up to ~31 days `isVerified()` is true for a person whose CIE has expired, while the home page says the badge "expires with the card". During that window the daily OCSP recheck still queries certificates that are already expired; depending on how the Ministry responder treats them, this may produce `error`/`unknown` answers and the new "revocation errors in two consecutive runs" alarm (UCL-06) every month.

**Recommendation.** Round **down**: `Date.UTC(year, month, 1)` (first day of the expiry month). It reveals exactly the same information (the month), never exceeds the card validity, and keeps the monthly bucket that hides the day. Skip OCSP for links whose certificate `notAfter` has passed (store the month in `cert_ref_enc`). Update the test and the page text accordingly. Contract unchanged.

### UCL-35 — Certificate reference kept after renunciation or owner revocation (Low)

**Where:** `backend/src/indexer.js` (`Invalidated` and `Revoked` branches), `backend/src/revocation.js:100` (cleanup only clears it when the badge **expiry** has passed).

**What happens.** When the backend itself invalidates a badge, `markInvalidated` clears `cert_ref_enc`. When the holder calls `renounce()` or the owner calls `revoke()` on-chain, the indexer only changes the status: the encrypted serial number and issuer stay until the link row is deleted, i.e. 12 months later. The notice says the reference "is deleted as soon as the badge expires or is invalidated".

**Recommendation.** Set `cert_ref_enc = NULL` in the indexer's `Invalidated` and `Revoked` branches, and in the cleanup for every link whose status is not `valid`. Add a test.

### UCL-36 — Operational details and the operator's personal data in the public repository (Low)

**Where:** `docs/operations.md` §1–2 (public on GitHub), `docs/audit/README.md`.

**What happens.** The public repository lists the VPS name and **public IP**, the SSH login user (`ubuntu@…`), the mail provider (`smtps.aruba.it`), all paths, service names, versions (nginx 1.18, Node, PM2) and the attester address. This is a ready-made map for an attacker (and it tells them the server hosts other projects). It also states that the first real link was made with UP `0xC014…` and a **real CIE** whose badge expires on 2034-03-01: it publicly ties that UP to the operator and reveals his month of birth (the live `/api/badge` and `/verifica` pages confirm the expiry).

**Recommendation.** Keep the runbook in the repository but move the host-specific values (IP, SSH user, provider, exact versions) to a private file or password manager, replacing them with placeholders. Remove the identifying description of the operator's own link (keep "first real link: OK, date"), unless the operator is fine with it being public. Note that git history keeps the old text; rewriting history is optional.

### UCL-37 — A real `.p7m` is copied to world-readable `/tmp` on a shared server (Low)

**Where:** `docs/operations.md` §2.4 (`scp <file>.p7m ubuntu@…:/tmp/cie.p7m`, later `shred -u`).

**What happens.** The file contains the holder's name, tax code and certificate. `scp` creates it with the remote umask (usually `0644`) in `/tmp`, readable by every local user and process of a VPS that also runs other projects, until the operator removes it.

**Recommendation.** Copy it into a private directory (`install -d -m 700 ~/p7m && scp … ~/p7m/`), or create it with restrictive permissions (`umask 077` on the remote side), and remove it right after the check as already documented. Better still, run `check-p7m.js` on the PC with the trust store and keep the server out of it.

### UCL-38 — Superseded testnet contracts may still have the live attester (Low)

**Where:** `contracts/deployments/luksoTestnet.json` (`superseded`: `0x056a7e72…7892`, `0x329DF2F4…4C2f`), same attester `0x8F42…723a`.

**What happens.** The old contracts were not shut down in the repository records. If their `attester` is still the live key, anyone who reads them (or any tool still configured with the old address) sees a working "UP CIE Link" badge contract whose badges are not managed anymore, and a leak of the attester key would also allow minting there. *Not verified on-chain (no RPC access from the audit environment).*

**Recommendation.** From the owner UP call `setAttester(address(0))` on each superseded contract and record it in the deployments file. Do the same for any future redeploy, as a step of the procedure.

### UCL-39 — Possible false "badge minted but not recorded" alert (Info)

**Where:** `backend/src/indexer.js:65-76`.

When `attest` times out (`TX_TIMEOUT`) and is mined later, the indexer can see the `Attested` event before `reconcileMints()` has closed the mint, and sends an `attested_unrecorded` **problem** e-mail although nothing is wrong. Have the indexer skip the alert when an open `mints` row exists for that UP (or check `mints.tx_hash`).

### UCL-40 — Small hardening items on the live site (Info)

Observed live (passive):

- `/api/config` advertises `cieChannels: ["cades", "raw"]`: the raw (Android) channel is open although the app does not exist yet. Put it behind a configuration switch like `ALLOW_CADES_UPLOAD`, off until the app ships.
- There is no `/.well-known/security.txt` (RFC 9116); unknown paths return the SPA page with status 200. Add a `security.txt` with the security contact.
- API responses carry `Referrer-Policy` and `X-Content-Type-Options` twice (backend and nginx). Harmless; drop one copy.
- `/README.md` (the frontend README) is served from the web root. Harmless (the repository is public); exclude non-site files if you prefer a clean web root.

### UCL-41 — Exception rejection cool-down counted from the request date (Info)

**Where:** `backend/src/linking.js` (`EXCEPTION_REJECTED` uses `request.created_at`). If the owner rejects a request 29 days after it was made, the person can file a new one the next day. Store `rejected_at` and count from it.

### UCL-42 — Local Windows working copy still partly CRLF (Info)

In `C:\Users\scava\Downloads\up-cie-link`, 35 tracked files still have CRLF line endings (checked out before `.gitattributes` existed); `git status` is clean because git normalises them. `badge.json` and `selftest.sh` are already LF, so nothing breaks today. Run `git rm --cached -r . && git reset --hard` (or a fresh clone) to normalise.

### UCL-43 — nginx 1.18: check the operating system's support status (Info)

`docs/operations.md` records nginx 1.18 (the reason HTTP/2 was not enabled). That version ships with Ubuntu 20.04 and 22.04; Ubuntu 20.04's standard support has ended, so if the VPS runs it, security updates require Ubuntu Pro/ESM. Check `lsb_release -a` and plan an upgrade if needed; it would also allow per-site HTTP/2.

## Appendix A — PoC used for the UCL-05 residual

```solidity
// SPDX-License-Identifier: Apache-2.0
pragma solidity 0.8.28;

interface IBadge2 { function renounce() external; }

/// Fake Key Manager: claims LSP6 and points to the fake UP.
contract AuditFakeKM {
    address public target;
    function setTarget(address t) external { target = t; }
    function supportsInterface(bytes4 id) external pure returns (bool) { return id == 0x01ffc9a7 || id == 0x23f34c62; }
}

/// Fake UP: claims LSP0 + LSP1, owner() = fake KM, accepts any ERC-1271 signature, optionally renounces during mint.
contract AuditFakeUP2 {
    address public badge;
    address public owner;
    bool public reenter;
    constructor(address badge_, address km, bool reenter_) { badge = badge_; owner = km; reenter = reenter_; }
    function supportsInterface(bytes4 id) external pure returns (bool) {
        return id == 0x01ffc9a7 || id == 0x24871b3d || id == 0x6bb56a14;
    }
    function isValidSignature(bytes32, bytes memory) external pure returns (bytes4) { return 0x1626ba7e; }
    function universalReceiver(bytes32, bytes calldata) external payable returns (bytes memory) {
        if (reenter && msg.sender == badge) IBadge2(badge).renounce();
        return "";
    }
}
```

Observed on `64ec68d`: `isUniversalProfile(fake) = true`, any 65-byte signature accepted; with `reenter = true` `attest` → `SIMULATION_REVERTED` (nothing sent, the queue continues); with `reenter = false` the fake UP is minted. This matches the residual recorded in `docs/audit/README.md`. If you want to close it, accept only Key Managers whose runtime code hash matches the official LSP6 implementations/proxies.

## Appendix B — Severity scale

- **Critical:** direct loss of funds/keys or mass exposure of personal data, exploitable now.
- **High:** core function broken or stoppable by an outsider, or serious integrity/privacy impact with a realistic path.
- **Medium:** significant weakness needing specific conditions, or a compliance gap that must be closed before real users.
- **Low:** hardening, defence in depth, limited impact.
- **Info:** documentation, hygiene, cosmetic.
