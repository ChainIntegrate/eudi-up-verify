## 1. Executive summary

The project kept improving at the same pace. The two big pieces since the last audit are well executed:

- **Signer process (UCL-08).** The attester key, `UNIQ_PEPPER` and `CERT_REF_KEY` now live in a separate process with its own user, **no network** (`PrivateNetwork`, `IPAddressDeny=any`, `AF_UNIX` only), root-owned code in `/opt`, secrets in a root-only env file, a strict systemd sandbox, and a narrow API: it signs only `attest`/`invalidate` on the configured contract and chain, with value 0 and capped gas, under rate limits. The backend refuses to start if the secrets are still in its `.env`, and checks a pepper check value and the `CERT_REF_KEY` on a stored reference. This is a solid design.
- **UP Wallet through WalletConnect.** The third-party code is loaded only when a person chooses UP Wallet, with Subresource Integrity, telemetry muted, and the CSP opened only to Reown's relay and Verify service. I **rebuilt both vendored files from npm and got byte-identical results** (same SHA-256), and `npm audit` of the 41 bundled packages reports nothing.

Verification results:

- All 30 commits' fixes for UCL-31 … UCL-43 are in place. Re-run PoCs: UCL-01 (no stall after a reverting call) and UCL-05 (re-entrant mint refused by the simulation) still hold with the signer in the loop.
- **Tests:** contracts 28/28, backend **127/127** (was 105), all passing.
- **Live site:** all **18** static files served (pages, JS, CSS, images, badge metadata, `security.txt`, the two vendored bundles) are byte-identical to `71a5fff`. Headers are correct and no longer duplicated, `/api/health` and `/README.md` answer 404, the Android raw channel is off, and every invalid or unauthenticated request I sent got the expected error code (400/401/403/404/413), never a stack trace. A page load contacts no third party.

What still needs attention:

1. **UCL-44 (Medium, new):** the self-service data requests accept a signature from **any UP that was ever linked to the person**, including UPs they migrated away from or renounced. Whoever controls such an old UP today (for example the attacker whose theft of that UP's key caused the migration) can download the list of all the person's UPs and erase their data, which invalidates their current badges. Confirmed with a PoC.
2. **UCL-45 (Medium, new, dependency):** the backend ships `body-parser 2.3.0` (through Express 5.3.0), affected by a published high-severity denial-of-service advisory on compressed request bodies (fixed in 2.4.0). The API accepts compressed bodies by default and is reachable without authentication. Not tested online (it would be an attack).
3. **Lower-severity points:** one CIE holder can exhaust the signer's global mint quota by renewing their own badge repeatedly (UCL-46, PoC); the signer still answers about 43 000 person-key requests a day to a compromised backend (UCL-47); the same attester key is planned for mainnet although it lived in the backend's `.env` before UCL-08 (UCL-48); the archived second audit report in the public repository repeats the operator details that UCL-36 removed (UCL-49); privacy notice and WalletConnect licence residuals (UCL-50, UCL-51); other dependency advisories (UCL-52).
4. **Still open by decision:** off-site backups (UCL-25).

## 3. New findings

### UCL-44 — A UP formerly linked to a person can export and erase all of that person's data (Medium)

**Where:** `backend/src/subject.js` (`personOf`, `execute`), `POST /api/subject/request`, page "Il mio bollino".

**What happens.** The request is authorised by an ERC-1271 signature of the UP named in the challenge. The person is then found through **any** row of `links` for that UP, whatever its status, and the export or erasure covers **every** UP of that person. `links` rows are kept for 12 months after a badge ends (invalidated, migrated away, renounced, revoked). So control of a UP *today* is taken as proof of being the person who linked it *in the past*.

Realistic case: a person migrates their primary badge to a new UP because the controller key of the old UP was stolen. The thief, who still controls the old UP, signs a data request with it and

- **export:** receives the list of all the person's UPs (the new primary, additional ones), dates and statuses — exactly the linkage the design keeps private;
- **erase:** deletes the person's records and queues on-chain invalidation of their **current** valid badges.

The same applies to a UP that was handed over to someone else, or that received an additional controller after being linked.

**Evidence (PoC, Appendix A.1, real `subject.js` and database schema):**

```
export signed by old UP X -> 0x1111 invalidated, 0x2222 valid
erase signed by old UP X -> erased 2 UP(s); queued on-chain invalidations: 0x2222 ERASED
```

**Recommendation.**
- Accept a data request only from a UP whose link is **currently valid** (`status = 'valid'`), and say so on the page; for a UP with an ended link, limit export and erasure to that UP's own row.
- For erasure of everything, or for a person with no valid link left, require a fresh **CIE signature** of the request (the same channel as linking): it proves the person, not just the UP.
- Notify the person's other UPs' holder? Not possible off-chain; at least log and e-mail the owner on every self-service erasure (already done) and export.

### UCL-45 — `body-parser 2.3.0`: published denial-of-service advisory, reachable without authentication (Medium)

**Where:** `backend/package-lock.json` (`express@5.3.0` → `body-parser@2.3.0`); `backend/src/app.js:96` (`express.json`) and `:199` (`express.raw`).

**What happens.** `npm audit` reports GHSA-27r3-jxmh-p828, *"body-parser vulnerable to Denial of Service via trailing bytes after a compressed request body"*, severity high (CVSS 7.5), affected `>=2.0.0 <2.4.0`; `body-parser@2.4.0` is available. Both parsers run with the default `inflate: true`, nginx passes `Content-Encoding` through, and the JSON parser is applied to every API route, including unauthenticated ones. The advisory details were not available from the audit environment and I did not test the live service (it would be an attack), so the exact impact on this service is not measured.

**Recommendation.** Update the lockfile (`npm update body-parser`, or an `overrides` entry `"body-parser": "2.4.0"` until Express ships it) and redeploy. Independently, set `inflate: false` on `express.json` and `express.raw`: the site never sends compressed bodies, so this removes the attack surface for good.

### UCL-46 — Unlimited renewals let one CIE holder exhaust the signer's global mint quota (Low)

**Where:** `backend/src/linking.js` (renewal branch of `decide`), signer limits `attestPerHour: 20`, `attestPerDay: 100`.

**What happens.** A person whose link is valid can renew the same UP again and again: `decide()` accepts every renewal with no cool-down, and every renewal is a real `attest` that spends the signer's **global** quota. CIE signatures can be automated with the official middleware and a card reader, and UP signatures with one's own controller key, so one CIE holder can use up the 20/hour and 100/day quota and block everyone else's links (`MINT_RATE_LIMITED`) until it resets. Migrations are already limited (one per 30 days); renewals are not.

**Evidence (PoC, Appendix A.2):**

```
decide(): 50/50 renewals of the same UP by the same person accepted, no cool-down
signer: 20 attest signatures, then RATE_LIMITED for everyone (hourly cap)
```

**Recommendation.** Allow a renewal only when it changes something (new card: different certificate serial or later expiry), or at most once every N days per person; add a per-person daily cap in the backend before calling the signer. Keep the global signer limit as the last line of defence.

### UCL-47 — The signer is still a person-key oracle for a compromised backend (Low, residual of UCL-08)

**Where:** `signer/src/core.js` (`personKey`, limit `personKeyPerMinute: 30`).

**What happens.** The separation protects the pepper itself, but whoever controls the backend can still ask the signer for `HMAC(pepper, tax code)` of any tax code, up to 30 per minute, i.e. about **43 000 per day**, with no daily cap. A person's tax code is computable from public data, so targeted re-identification ("which UPs belong to this person?") stays possible after a backend compromise, and the volume allows a sizeable dictionary of candidates. The same backend can also have up to 100 badges a day minted and 100 an hour invalidated (bounded by the limits, as designed).

**Recommendation.** Add a **daily** cap on person keys close to real traffic (each link needs exactly one), and an alert from the signer side that does not depend on the backend (for example the monitor reading the signer's `status` counters, or a journal alert on refusals). Record this residual in the threat model.

### UCL-48 — Attester key planned for mainnet was stored in the backend's `.env` before UCL-08 (Low)

**Where:** `docs/operations.md` (attester "la stessa anche per il mainnet, decisione A3").

**What happens.** Until 27 October the attester private key sat in `backend/.env` on a VPS shared with other projects, readable by the backend's user, and it was copied by hand during the migration to the signer. Reusing it for mainnet carries that whole history into the network where badges matter.

**Recommendation.** For mainnet, generate a **new** attester key directly into `/etc/up-cie-link/signer.env` (never on the PC that keeps the other copies, never in the backend), keep the testnet key for testnet only, and deploy the mainnet contract with the new attester.

### UCL-49 — The archived second audit report repeats the operator details removed under UCL-36 (Low)

**Where:** `docs/audit/AUDIT-2026-10-15.md` (public), kept "without changes" by policy.

**What happens.** UCL-36 removed from `docs/operations.md` the identifying description of the operator's own link. The archived report, committed afterwards, still names that UP address, ties it to the operator's real CIE, states the month of birth it reveals, and repeats the SSH login user. My report did that while describing the problem; publishing it unchanged undoes the fix.

**Recommendation.** Publish a redacted copy (replace the UP address, the expiry and the inferred month, and the SSH user with placeholders) and keep the full report private, or accept the disclosure explicitly. Git history keeps the old text either way; rewriting history is optional. This third report avoids those details on purpose.

### UCL-50 — Privacy notice residuals (Low)

**Where:** `frontend/js/i18n.js` (`privacy`, both languages; live = repository).

- §7 says rectification and restriction can be requested from "Il mio bollino"; the page offers only export and erasure. Either add a "restrict" option (for example: stop the daily OCSP recheck and suspend the badge) or say these requests go by e-mail, signed with the UP.
- Reown is disclosed as a US company with processing possibly outside the EU, but the **transfer safeguard** is not named (EU–US Data Privacy Framework certification, if Reown is certified, or standard contractual clauses), as Art. 13(1)(f) GDPR asks.
- The controller is still "ChainIntegrate, servizi di Simone Cavalletti" with e-mail and Telegram, without postal address or VAT number (owner's decision of 27 October; to add when the activity is formalised).

### UCL-51 — WalletConnect Community License: notice placement and terms to watch (Low)

**Where:** `frontend/vendor/`, `NOTICE`, legal notes page, connection window.

- The licence (§2(a)) asks for the notice "Portions © 2025 Reown, Inc. All Rights Reserved" in the readme of the product **or the about section of the website**. It is in `NOTICE`, in `vendor/README.md` and in the WalletConnect window; the site's legal notes page still says only "the code is public under the Apache-2.0 licence". Add a line there about the third-party components and their licences.
- Terms to keep in mind: §3 thresholds (500 monthly active users or 2.5 million RPC calls) above which a paid licence is required; §1(c) assigns to Reown rights in modifications of its code (the bundle is unmodified, rebuilt exactly from npm: keep it that way); §7 (confidentiality) sits oddly with publishing the bundle in a public repository — acceptable for testnet, worth a legal check before commercial use.

### UCL-52 — Other dependency advisories (Low)

- **Backend `nodemailer@10.0.13`:** three moderate advisories in the address parser (affected `<10.1.4`, fixed in 10.2.1). Not exploitable here — the backend sends only to the fixed `NOTIFICATION_EMAIL` — but update it together with UCL-45.
- **Contracts (build tooling only):** 15 advisories (14 high, 1 low) in the Hardhat 3 toolchain (`undici`, `zod`, `serialize-javascript`, propagated to the Hardhat plugins). Nothing is deployed from these packages and `npm ci --ignore-scripts` is used; update Hardhat 3 (current 3.21.1) and the toolbox when the fixed transitive versions are picked up. `npm audit fix` proposes a downgrade to Hardhat 2: do not apply that.
- Signer (`ethers` only) and spike: 0 advisories. The 41 packages inside the WalletConnect bundle: 0 advisories.

### UCL-53 — Signer limits will need raising with growth (Info)

The daily revocation recheck decrypts one certificate reference per active badge, and the signer allows 2 000 decryptions a day (plus one at every backend start). Above about 2 000 active badges the recheck starts failing with `RATE_LIMITED` and the "revocation errors" alarm fires. Similarly, 100 mints a day caps growth. The e-mails would tell, but plan the values (or make the decrypt limit scale with the number of active links reported at start-up).

### UCL-54 — Badges issued before the UCL-34 fix keep the later expiry (Info)

Badges minted between 15 and 27 October expire on the first day of the month **after** the card expiry, so they can outlive the card by up to a month. The tracking notes this; on testnet it is harmless. Before mainnet nothing is needed (new contract); on testnet, renewing them would align them.

## Appendix A — PoC code

### A.1 Data request signed by a UP whose link has ended (UCL-44)

```js
import assert from "node:assert/strict";
import { test } from "node:test";
import { mkdtempSync } from "node:fs";
import { tmpdir } from "node:os";
import path from "node:path";
import { openDb } from "../src/db.js";
import { createSubjectRequests } from "../src/subject.js";

test("old UP controls the person's data", async () => {
  const db = openDb(path.join(mkdtempSync(path.join(tmpdir(), "subj-")), "t.db"));
  const P = Buffer.alloc(32, 7);
  const now = Date.now();
  const X = "0x1111111111111111111111111111111111111111"; // old UP: migrated away / renounced
  const Y = "0x2222222222222222222222222222222222222222"; // current primary
  db.prepare("INSERT INTO persons (person_key, created_at) VALUES (?, ?)").run(P, now);
  const ins = db.prepare("INSERT INTO links (up, person_key, is_primary, status, verified_at, expires_at, updated_at) VALUES (?, ?, ?, ?, ?, ?, ?)");
  ins.run(X, P, 0, "invalidated", now - 86400e3, now + 365 * 86400e3, now - 3600e3);
  ins.run(Y, P, 1, "valid", now - 3600e3, now + 365 * 86400e3, now - 3600e3);
  const cfg = { publicOrigin: "https://x", deployment: { chainId: 4201 } };
  // whoever controls UP X today can produce a valid ERC-1271 signature
  const subject = createSubjectRequests({ db, cfg, upChecker: { isValidUpSignature: async () => true } });

});
```

## Appendix B — Severity scale

- **Critical:** direct loss of funds/keys or mass exposure of personal data, exploitable now.
- **High:** core function broken or stoppable by an outsider, or serious integrity/privacy impact with a realistic path.
- **Medium:** significant weakness needing specific conditions, or a compliance gap that must be closed before real users.
- **Low:** hardening, defence in depth, limited impact.
- **Info:** documentation, hygiene, cosmetic.
