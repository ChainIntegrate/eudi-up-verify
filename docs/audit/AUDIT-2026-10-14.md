## 1. Executive summary

The project is carefully designed and unusually well documented for a proof of concept. Several things are done right: the CIE certificate chain is validated explicitly with OpenSSL (after the team found that pkijs path building was unsafe), OCSP is fail-closed, the signed content is compared byte for byte, personal data is kept out of logs (and tests assert it), the frontend loads no third-party code under a strict CSP and never injects network data as HTML, SQL is parameterised, dependencies are pinned, backups are encrypted to an offline public key, and the contract is small, soulbound and well tested. All 25 contract tests and all 63 backend tests (including the Chromium end-to-end test) pass.

The most important problems found:

1. **One failed transaction stops all minting until the process is restarted (UCL-01, High).** The attester uses ethers' `NonceManager`, which consumes a nonce *before* gas estimation. Any revert or RPC error leaves a nonce gap; on a real LUKSO node the next transaction is queued forever and the serial queue never moves again. Any person with a valid CIE can trigger this on purpose (PoC included), and the monitor does not detect it.
2. **The link page tells users their statement has expired 5 minutes after it was created (UCL-02, High).** Countdown timers from earlier steps keep running: during the CieSign step the page switches to "Enunciato scaduto" and forgets the statement, although the backend still accepts the upload for 10 more minutes. The success page is overwritten in the same way at 15 minutes. In practice this breaks the main user flow (PoC in Chromium).
3. **"No personal data on-chain" does not fully hold (UCL-03, Medium).** `expiresAt` is the certificate's `notAfter`; Italian identity documents expire on the holder's birthday, so the badge very likely publishes day and month of birth. The identical timestamp on every UP of a person, and the back-to-back `invalidate`/`attest` of a migration, also link a person's UPs publicly — contrary to the stated design.
4. **Uniqueness and on-chain/off-chain consistency can be broken** by a restart during minting (UCL-04), by "UP-like" contracts that re-enter `renounce()` while the badge is minted (UCL-05, PoC), and the daily revocation recheck can stop working without any alert (UCL-06).
5. **Compliance work is still open before real users:** data retention and erasure are not implemented (UCL-10), there is no age check although CIEs are issued to minors (UCL-11), and the CieSign terms of use / CIE certificate policy for a private relying party are still unverified (UCL-13).
6. **Supply chain:** a mistaken runtime dependency inside the LUKSO packages pulls ~560 packages (web3 1.x, 61 advisories, a `git+ssh` dependency, install scripts) into the contracts project, which is installed in Codespaces next to the deployer key (UCL-09).

## 2. System overview (as audited)

```
Browser + UP Browser Extension ──► nginx (TLS, CSP, static frontend) ──► Express backend 127.0.0.1 (PM2)
                                                                         ├─ SQLite (statements, links, persons, audit, outbox)
                                                                         ├─ LUKSO RPC ──► UpCieBadge (attest / invalidate)
                                                                         └─ Ministry OCSP (fail-closed)
systemd timers: hourly monitor (read-only), daily age-encrypted backup
```

Flow: `POST /api/statements` → UP signs the statement (EIP-191, checked with ERC-1271) → the user signs the downloaded statement with CieSign (CAdES `.p7m`) and uploads it → backend verifies CMS, certificate (validity, key usage, policy `1.3.76.47.4`), chain to a pinned root, OCSP → `person_key = HMAC(UNIQ_PEPPER, tax code)` → serial queue: uniqueness decision, optional `invalidate(old, "MIGRATED")`, `attest(up, "CIE", notAfter, primary)` → `links` row. An indexer mirrors contract events; a daily job rechecks OCSP and invalidates revoked cards.

Trust boundaries: the internet-facing Express process holds the attester hot key, the pepper and the database; the owner is a ChainIntegrate UP (multi-controller, offline from this server); deployment runs from GitHub Codespaces with `DEPLOYER_PRIVATE_KEY` as a secret.

## 3. Detailed findings

### UCL-01 — Minting pipeline stalls permanently after one failed transaction (High)

**Where:** `backend/src/chain.js:37-41` (`createMinter`), used by `backend/src/cieFlow.js:114,122` and `backend/src/revocation.js` through the serial queue `backend/src/queue.js`.

**What happens.** The minter wraps the attester wallet in ethers v6 `NonceManager`. Its `sendTransaction` increments the local nonce counter *before* `populateTransaction` runs `estimateGas`:

```js
// ethers 6.17.0, providers/signer-noncemanager.js
const noncePromise = this.getNonce("pending");
this.increment();                               // nonce consumed here
tx = await this.signer.populateTransaction(tx); // estimateGas: a revert or RPC error throws here
tx.nonce = await noncePromise;
```

`reset()` is never called. After any failure at that point every later transaction is signed with a nonce that leaves a gap:

- on Hardhat (automine) it is rejected: *"Nonce too high. Expected nonce to be 1 but got 2"*;
- on a geth-style node such as LUKSO it is **accepted into the queued pool and never mined**. `tx.wait(confirmations)` has no timeout, so the job never ends and the **serial queue blocks every later link and every revocation invalidation** until the process restarts. After a restart the queued transaction can still be mined, minting a badge for a statement already marked `INTERRUPTED` (which feeds UCL-04).

**Triggers** (any of them is enough):

- *Deliberate, by any CIE holder:* deploy a contract that answers `supportsInterface(LSP0) = true` and returns the ERC-1271 magic value for any signature, but does not support LSP1. It passes `isUniversalProfile` and `isValidUpSignature`; after a valid CIE signature `attest()` reverts (`_mint(..., force=false)` requires LSP1). Repeatable after every restart.
- A real UP whose Universal Receiver Delegate rejects LSP8 tokens.
- `migrate` (or the daily revocation recheck) calling `invalidate()` on a badge the holder has just renounced, before the indexer (1 min + 2 blocks) has caught up → `BadgeNotValid` revert.
- UCL-05 desynchronisation, a transient RPC error, or an attester balance too low for gas.

**Evidence (PoC, Appendix A.1/A.2):**

```
1st failure: execution reverted (unknown custom error)      ← invalidate() of a non-valid badge
2nd (valid) attest: FAILED: Nonce too high. Expected nonce to be 1 but got 2
3rd (valid) attest: FAILED
--- node with a mempool (auto-mining off, 1 s interval) ---
attest(up2) (valid): STILL PENDING after 20 s | latest nonce: 1  (tx was sent with nonce 2)
```

**Detection:** none. `/api/health` returns the queue length but `monitor.js` does not evaluate it, and no check looks for statements stuck in `queued`/`minting`.

**Recommendation.**
- Drop `NonceManager`: the queue is already serial, so a plain `Wallet` (nonce read from the node each time) is enough. If you keep it, call `signer.reset()` in a `catch` around every send.
- Simulate before sending (`contract.attest.staticCall(...)` / `estimateGas`) and turn a revert into a clean `MINT_FAILED` without touching the nonce.
- Use `tx.wait(confirmations, timeoutMs)`; on timeout, replace the transaction with the same nonce and a higher fee, or alert.
- Monitor: alert when the queue is non-empty for more than N minutes or when statements stay in `queued`/`minting` longer than N minutes.
- Add a regression test "revert, then a valid attest succeeds" (Appendix A.1 can be used as is).

### UCL-02 — Stale countdowns abort the CIE step after 5 minutes and overwrite the success page (High)

**Where:** `frontend/js/app.js:417-434` (`countdown`), used at `:285` (UP-signature deadline) and `:329` (statement expiry); cleanup only in `leavePage()` (`:23`), which runs on route changes.

**What happens.** `countdown()` registers its `setInterval` for cleanup with `onLeave()`, but the steps of the link flow are redrawn inside the same route with `draw()`, so earlier timers are never cleared. When the hidden UP-signature countdown (issuance + 5 min) reaches zero it calls `expired()`: the CIE step is replaced by **"Enunciato scaduto / Statement expired"**, the upload form disappears and `sessionStorage` is cleared, although the backend accepts the `.p7m` until issuance + 15 min. The CIE countdown does the same at 15 min, replacing the "waiting" or **success** page.

**Evidence (PoC in Chromium with Playwright's fake clock, Appendix A.3):**

```
CIE step shown; statement 02bff9d9-…
after 5:10 → page shows 'Enunciato scaduto': true | upload field visible: false | backend status: pending_cie
success page shown: true → after 15:10 → success still shown: false | 'Enunciato scaduto' shown: true
```

**Impact.** The real CieSign path (download the file, move it to the phone, NFC + PIN, move the `.p7m` back, upload) regularly takes more than the ~4 minutes left after the UP signature. Most real users would be told to start over; the existing e2e test does not catch it because it completes in seconds.

**Recommendation.** Keep the flow's timers in a list cleared at every `draw()`, or let `countdown()` stop itself when its element is no longer in the document (`if (!el.isConnected) return clearInterval(timer)`). Show the UP deadline only during the UP step. Add an e2e test with `page.clock` (Appendix A.3).

### UCL-03 — On-chain `expiresAt` reveals the holder's birthday and links all UPs of a person (Medium)

**Where:** `backend/src/cieFlow.js:62` (`expiresAtSec = notAfter`), contract `Attested` event / `getAttestation`, `frontend/js/app.js` verify page (shows the expiry date publicly); decision D4.

**What happens.**

1. **Birthday.** Under Italian law identity documents are issued "with validity up to the date corresponding to the holder's day and month of birth immediately following the normal expiry" (D.L. 5/2012, art. 7(2), converted by L. 35/2012 — *auditor's knowledge, to be confirmed*). The spike records that the certificate validity matches the card validity (~7.3 years left). If the certificate `notAfter` equals the printed expiry, every badge publishes the holder's **day and month of birth**, permanently, on a public chain and on the public `/verifica/<up>` page. The validity length also hints at an age band (3/5/10-year cards). *To confirm:* compare the printed expiry of the test CIE with the `notAfter` printed by the spike.
2. **Linkability.** The same `notAfter` (second precision) is written on **every UP of the same person**: primary, additional and the old/new UP of a migration. Clustering UPs by `expiresAt` is trivial. This contradicts the README ("a person's additional UPs … are never linked on-chain") and decision 1 of `docs/01-contratto.md`.
3. **Migration timing.** `invalidate(old, "MIGRATED")` and `attest(new, primary)` are sent back to back by the same attester (consecutive nonces, usually the same or the next block), which links the two UPs even without point 2.
4. **Revocation reason.** `Invalidated(..., "CERT_REVOKED")` publicly states that the holder's card was revoked (lost, stolen, replaced, or the holder died).

**Recommendation.**
- Decouple the badge expiry from `notAfter`, e.g. `expiresAt = min(notAfter, verifiedAt + 12 months)` rounded **down** to the first day of the month (or quarter), so it carries neither the birthday nor a per-person fingerprint. Keep `notAfter` off-chain (encrypted) if renewal reminders need it.
- Use one generic invalidation reason on-chain (e.g. `"INVALIDATED"`), keep the precise reason off-chain.
- For migrations, delay the `invalidate` of the old UP by a random interval and batch it with other operations, or state clearly in the notice that a migration is publicly linkable.
- Correct the "no personal data on-chain" wording (see UCL-10).

### UCL-04 — "One person, one primary UP" breaks when a mint is not recorded (Medium)

**Where:** `backend/src/cieFlow.js` (`process`, person key only in memory), `failInterrupted` (`:161`), `backend/src/indexer.js:65-76`.

**What happens.** The person key exists only in the queued job. If the process stops between broadcast and `applyLink` (PM2 restart at 300 MB, deploy, crash, OOM) or `tx.wait` throws after broadcast (RPC timeout), the badge is minted as **primary** on-chain but no `links` row exists. The same person can then link another UP with mode `link` and get a second primary badge. The indexer only sends an `attested_unrecorded` email and asks for manual action. UCL-01 makes this more likely (a queued future-nonce transaction mined after the restart).

**Recommendation.** Inside the queue, write a pending row (`person_key`, `up`, `status='minting'`, planned role) *before* sending, store the transaction hash as soon as it is known, and finalise after the receipt. On start-up, reconcile pending rows against receipts / `getAttestation()` instead of failing them blindly. Treat an unknown `Attested` event as blocking until resolved.

### UCL-05 — UP-like contracts accepted; re-entrant `renounce()` during mint desynchronises events and state (Medium)

**Where:** `backend/src/up.js:18-28`; `contracts/contracts/UpCieBadge.sol:85-104` (`attest`: state written, then `_mint` calls the recipient's `universalReceiver`, then `emit Attested`); `backend/src/indexer.js` (applies events in log order).

**What happens.**
- The backend accepts any contract that claims the LSP0 interface and returns the ERC-1271 magic value. Such a contract may have arbitrary rules (e.g. anyone can execute through it), so "verified UP" does not guarantee a single controller, and it can be used to trigger UCL-01.
- During `_mint` the recipient can call `renounce()`. The final state is `Invalidated`, but the events are emitted as **`Invalidated` → `Attested`**. The backend indexer (and any third-party indexer) applies them in order and ends with `valid`, while `isVerified()` returns `false`. Consequences: the person is blocked by the local DB (`MIGRATION_OR_EXCEPTION_REQUIRED`); a later `migrate` makes `invalidate()` revert, which triggers UCL-01.

**Evidence (PoC, Appendix A.4):**

```
isUniversalProfile(fake): true
isValidUpSignature(fake, any 65-byte sig): true
events in the attest tx, in log order: Invalidated -> Attested
on-chain isVerified(fake): false  status: 2 (Invalidated)
```

**Recommendation.**
- Contract (requires redeploy): emit `Attested` before `_mint`, and/or re-check `a.status == Valid` after `_mint` and revert otherwise; or add a reentrancy guard shared by `attest` and `renounce`.
- Indexer: for each transaction touching a UP, read `getAttestation()` at that block as the source of truth instead of replaying events blindly.
- Backend: verify the UP more strictly (e.g. `owner()` is an LSP6 Key Manager whose `target()` is the UP, and/or a known LSP0 implementation code hash), and simulate `attest` (`staticCall`) before queueing.

### UCL-06 — Revocation recheck can fail silently; strict OCSP path untested against the real responder (Medium)

**Where:** `backend/src/revocation.js:67-81`; `backend/src/cie/ocsp.js:32-56`; `backend/src/monitor.js`.

**What happens.**
- The "3 days unavailable" alert counts only `OCSP_UNAVAILABLE`. If every recheck ends in `error` (`OCSP_INVALID`, `ISSUER_NOT_IN_TRUST_STORE`, e.g. after a responder-certificate rotation, an RSA-PSS signature, or a new sub CA not in `trust/`), the streak is **reset** and nothing is reported. The monitor does not read the `revocation` result either. Revoked cards would then keep valid badges indefinitely.
- `ocsp.js` accepts only responses signed by the issuing CA or by a delegated responder issued *directly* by it with `id-kp-OCSPSigning`. The spike validated the real Ministry response with pkijs (more lenient), and the docs state the backend has not been run with a real CieSign file. If the real responder certificate does not match these rules, **every real verification fails closed** and the service cannot link anyone.

**Recommendation.** Before launch, run `verifyCieCades` on the spike's real `.p7m` against the real OCSP (keep only a non-personal fixture, e.g. the responder certificate). Alert when the error count is > 0 for 2 consecutive runs or when the last revocation run is older than 36 h. Add the outcome counts to the daily summary.

### UCL-07 — CIE signature not bound to the requesting session: phishing and signature farming (Medium, design)

**Where:** protocol design; `POST /api/statements/:id/cie-cades` accepts the upload from anyone who knows the statement id.

**What happens.** An attacker creates a statement for **their own** UP, signs it with that UP, and convinces a victim to "sign this file with CieSign to verify your identity" (people rarely read the content of a `.txt` they are asked to sign). The victim's CIE becomes the attacker's primary badge. The victim can recover only by migrating. The same mechanism enables buying CIE signatures to create "verified" UPs. The analysis (§1) acknowledges collusion; phishing of unaware holders is not addressed.

**Recommendation.** In the statement text, add an explicit warning ("Sign only if you started this request yourself on up-cie-link.chainintegrate.it for your own Universal Profile 0x…"). In the Android app (A2) show the UP address and purpose on the device before the PIN. Limit migrations per person per period, and give holders a simple way to report misuse (owner `revoke`).

### UCL-08 — Secrets and data co-located on the internet-facing host (Medium)

**Where:** `backend/.env` (loaded by `config.js`), `deploy/ecosystem.config.cjs`, `deploy/systemd/*`.

**What happens.**
- `UNIQ_PEPPER` sits on the same host and in the same process as the database. With the pepper, re-identifying a known person needs no brute force: their tax code can be computed from public data (name, date and place of birth), so `HMAC(pepper, CF)` immediately shows which UPs belong to them.
- `ATTESTER_PRIVATE_KEY` is a hot key inside the web-facing process; a compromise allows arbitrary badges until the owner calls `setAttester(0)` (detection exists via `attested_unrecorded`, which is good).
- Neither `.env` nor the database file permissions are enforced (better-sqlite3 creates the DB with the process umask; PM2 sets none); the PM2-run backend has no systemd hardening.

**Recommendation.** Move HMAC and signing into a small separate process (or an HSM/KMS) under a different OS user; run the backend as a dedicated user with `UMask=0077` (systemd unit with `ProtectSystem=strict`, `ProtectHome`, `ReadWritePaths`, `NoNewPrivileges`, `PrivateTmp`), refuse to start if `.env` or the DB is group/world readable, keep the attester balance low.

### UCL-09 — Contracts dependency tree: accidental runtime dependencies in the deploy environment (Medium, supply chain)

**Where:** `contracts/package-lock.json`.

**What happens.** `@lukso/lsp4-contracts@0.17.3 → @lukso/lsp2-contracts@0.16.2 → @erc725/smart-contracts@7.0.0 → solidity-bytes-utils@0.8.0` declares `@truffle/hdwallet-provider@2.1.15` as a runtime dependency. This drags **561 production packages** (775 in total), including `web3@1.10.0` (end of life), `web3-provider-engine`, `ethereumjs-vm@2.6.0`, and `ethereumjs-abi` fetched from a **`git+ssh://` URL**. `npm audit --omit=dev`: **61 advisories (3 critical, 14 high, 34 moderate, 10 low)** — none is reachable at runtime (only `.sol` sources are used), but **8 packages of this chain run install scripts** (`bufferutil`, `es5-ext`, `keccak`, `secp256k1`, `utf-8-validate`, `web3`, `web3-bzz`, `web3-shh`) during `npm ci`, which `.devcontainer` runs in Codespaces where `DEPLOYER_PRIVATE_KEY` is exposed as an environment variable. The `git+ssh` dependency also makes `npm ci` fail in environments without GitHub SSH.

Backend and spike: `npm audit` reports **0** vulnerabilities.

**Recommendation.** Add an npm `overrides` entry that replaces `@truffle/hdwallet-provider` under `solidity-bytes-utils` with an empty package (or override `solidity-bytes-utils` to a version without it), run `npm ci --ignore-scripts` in the devcontainer and CI, keep deploy keys in the Hardhat encrypted keystore rather than plain env secrets, and fund the deployer only for the deployment.

### UCL-10 — GDPR data lifecycle: indefinite retention, no erasure tooling, inaccurate on-chain statement (Medium)

**Where:** `backend/src/db.js`, `backend/src/revocation.js:88-96` (`runCleanup`), `frontend/js/i18n.js` (privacy notice), `README.md`.

**What happens.**
- Only `statements` (7 days after expiry) and sent `notifications` (90 days) are ever deleted. `links` (UP ↔ person key, encrypted certificate reference), `persons`, `exception_requests` and `audit` are kept **forever**. The notice says the certificate reference is "deleted with the link", but links are never deleted, and the reference has no purpose once the badge is invalidated or expired (storage limitation, Art. 5(1)(e) GDPR).
- There is no script or procedure for access/erasure requests; erasure needs manual SQL. Deleting the person key also reopens "one person, one UP" — the policy for that trade-off is not written down (e.g. keep the HMAC for a defined period on the basis of legitimate interest in fraud prevention, with a balancing test, or accept the loss).
- The `audit` table and the notification e-mails (UP addresses, tickets) are not mentioned in the notice.
- "No personal data on-chain" (README, home page, notice) is not accurate: a UP address carrying an identity badge is pseudonymous personal data (many UPs also publish an LSP3 name and picture), and see UCL-03.

**Recommendation.** Define and implement retention per table (e.g. delete `cert_ref_enc` at invalidation/expiry, links N months after the end of validity, audit rows after 12 months), add `scripts/erase.js --up 0x…` / `--export` for data-subject requests, document the uniqueness trade-off, and reword the on-chain statement ("no name, tax code or card data on-chain; the badge itself, linked to your UP, is public and permanent").

### UCL-11 — No age check although CIEs are issued to minors (Medium)

**Where:** `backend/src/cie/verify.js:114,129-135`; notice §8 ("not meant for people under 18").

**What happens.** CIEs (with PIN) are issued from birth, so a minor can complete the flow; the notice only says the service is not meant for them. In Italy the age of consent for information-society services is 14 (art. 2-quinquies, Codice privacy — *to be confirmed by counsel*), and signing a declaration may raise capacity issues under 18.

**Recommendation.** The tax code encodes the birth date: reject holders under 18 (or the chosen threshold) in `extractTaxCode` before deriving the person key (resolve the two-digit year with the card validity; months are letters A–T, female days +40). Return a neutral error code and add a test.

### UCL-12 — Statement reported as `expired` while still verifying, queued or minting (Medium, bug)

**Where:** `backend/src/statements.js:70-71`.

**What happens.** `publicStatus()` reports `expired` for every non-terminal status once `expires_at` has passed — including `verifying`, `queued` and `minting`. A `.p7m` uploaded close to the deadline (common with CieSign), or a queue backlog, makes the frontend show "Statement expired, start again" while the badge is about to be minted; the user may restart and create duplicate work.

```
verifying -> expired | queued -> expired | minting -> expired
```

**Recommendation.** Apply lazy expiry only to `pending_up` and `pending_cie`.

### UCL-13 — CieSign terms and CIE certificate policy for a private relying party still unverified (Medium, legal)

**Where:** `docs/00-analisi.md` §4 (marked **[I]**: "Termini d'uso di CieSign e del Software CIE … da leggere"); not closed in later documents.

**What happens.** The whole service relies on (a) citizens using the Ministry/IPZS CieSign app to sign a statement for a private company and (b) ChainIntegrate relying on the CIE holder certificate (policy `1.3.76.47.4`) outside the "Entra con CIE" federation. Neither the app's terms of use nor the certificate policy/CPS have been checked. If either restricts this use, the service (and the badges already issued) may have to stop.

### UCL-15 — Rate limiting: per-IP only, unbounded map, RPC amplification (Low)

**Where:** `backend/src/app.js:18-31,64-65`.

The limiter keys on the full IP (an IPv6 /64 gives billions of keys), its map is only pruned of *expired* entries when it exceeds 10 000, so it can grow without bound inside one window, and `POST /api/statements` and `GET /api/badge/:up` each trigger RPC calls (on mainnet against the dedicated ChainIntegrate node). Recommendation: bucket IPv6 by /64, cap the map, add nginx `limit_req` per zone, and cache badge reads for a few seconds.

### UCL-16 — nginx template hardening (Low)

**Where:** `deploy/nginx/up-cie-link.conf`.

- Only `listen 80`; TLS is left to certbot and **no HSTS** header is set.
- `add_header` in `location /metadata/` and `location ~ ^/(js|css|img)/` replaces the server-level headers (nginx does not merge them), so `X-Frame-Options` and `Referrer-Policy` are missing there.
- The comment "do not log query strings" is inaccurate: the default `combined` format logs the full request line. Access logs pair client IPs with UP addresses (`/api/badge/0x…`, `/verifica/0x…`) — disclosed in the notice, but make sure log rotation really enforces 14 days.
- Consider `server_tokens off;`, a `Permissions-Policy`, and blocking `/api/health` from outside (UCL-23).

### UCL-17 — SMTP STARTTLS not enforced (Low)

**Where:** `backend/src/notify.js:24`. With `SMTP_SECURE=false` (port 587) nodemailer uses STARTTLS opportunistically; a downgrade sends credentials and notification bodies in clear. Set `requireTLS: true` when `secure` is false.

### UCL-18 — PKI hardening (Low)

**Where:** `backend/src/cie/ocsp.js`, `chain.js`, `verify.js`. OCSP requests carry no nonce and responses up to 2 days old are accepted (replay window for a revoked card); `sha1WithRSAEncryption` is accepted for OCSP and pkijs accepts SHA-1 CMS digests; chain validation ignores `pathLenConstraint`, name constraints and the revocation status of the sub CA; `extKeyUsage` is not checked. None is exploitable without a CA compromise or a network attacker, but restricting algorithms to SHA-256+ and tightening the OCSP window is cheap.

### UCL-19 — Daily OCSP recheck discloses users to the Ministry (Low, privacy)

Every day the server sends the serial number of every linked certificate to `ocsp.cie.interno.gov.it`. The Ministry can map serials to citizens and learns who uses the service. Downloading the CRL (once it parses correctly — see the spike note) would reveal nothing per user. At minimum, state this explicitly in the notice.

### UCL-20 — Migration is not atomic (Low)

**Where:** `backend/src/cieFlow.js:112-123`. If `invalidate(old)` succeeds and `attest(new)` fails, the person is left with no badge (they can link again). Attest the new UP first, then invalidate the old one (or record a compensating action).

### UCL-21 — Approved exceptions cannot be withdrawn or reduced (Low, contract)

**Where:** `UpCieBadge.sol:141-142`. `approveException` reverts for `maxUps < 2`, so the owner cannot cancel an exception granted by mistake (the backend treats `0` as "pending"). Allow `0` to revoke and any value ≥ 1 to reduce.

### UCL-22 — Monitor blind spots; monitor loads the attester private key (Low)

**Where:** `backend/src/monitor.js:192`. Missing checks: stuck queue / old `queued`-`minting` statements (UCL-01), revocation job errors and age (UCL-06), rising `MINT_FAILED`. The monitor is described as read-only but, without `ATTESTER_ADDRESS`, it loads `backend/.env` and derives the address from `ATTESTER_PRIVATE_KEY`. Give it its own environment file without secrets.

### UCL-23 — Public `/api/health` exposes internal state (Low)

**Where:** `backend/src/app.js:68`. Queue length and indexer progress are visible to anyone and help time an attack (e.g. UCL-01). Restrict it to localhost in nginx or return only `ok` publicly.

### UCL-24 — No `.gitattributes`: Windows checkout is CRLF (Low)

All 93 text files of the local working copy are CRLF (git index is LF). `frontend/metadata/badge.json` is hashed (keccak256 of the exact bytes) in the on-chain LSP4 `VerifiableURI`; deploying from a CRLF copy breaks metadata verification in wallets. `spike/selftest.sh` fails under bash with CRLF. Add `.gitattributes` (`* text=auto eol=lf`, `frontend/metadata/** -text`, `*.png binary`).

### UCL-25 — Backups on the same server; no key-rotation path (Low)

Accepted for now in B5, but a server loss loses both data and backups; required before mainnet. Losing `UNIQ_PEPPER` or `CERT_REF_KEY` is unrecoverable and there is no documented rotation (the HMAC input has a `v1` prefix and `cert_ref_enc` a version byte — good starting points). Write a rotation procedure and test restores monthly as planned.

### UCL-26 — Documentation drift (Info)

- `README.md` status table: Phase 2 "to do" (the backend is implemented), Phase 1 "redeploy needed" (done); the layout omits `backend/`, `frontend/`, `deploy/`.
- `docs/02-backend.md` §7 mentions `backup.sh` / `restore.sh` (they are `.js`); `docs/00-analisi.md` still says "bozza da approvare" and shows an older schema.
- The local repository is **one commit behind** `origin/main` (`7deb1e5`, docs only: `docs/03-frontend.md`). Pull before continuing.
- `UpCieBadge.sol` is unchanged since `ab0a1d0`, the commit recorded for the testnet deployment; the deployed bytecode itself could not be checked (no network).

### UCL-27 — No copyright holder stated (Info, licence)

`LICENSE` is the stock Apache-2.0 text; no file names a copyright holder (no `NOTICE`, no `author` in `package.json`, no headers beyond SPDX in the `.sol` files). 33 of 37 commits are authored by "Claude". Add a `NOTICE` (e.g. "Copyright 2026 ChainIntegrate") and, if useful for IP purposes, note the human review/ownership of the code.

### UCL-28 — Banner placeholder and clipped check mark (Info, cosmetic)

`frontend/img/banner.png` (shown on the public home page) contains the text "by ChainIntegrate · placeholder", and its check mark is visibly cut off: the SVG glow filter uses the default filter region, which clips the 44 px stroke (`img/src/banner.svg`). Set `filterUnits="userSpaceOnUse"` with an explicit region, or enlarge `x/y/width/height` of the filter.

### UCL-29 — Test data and tax-code edge cases (Info)

Tests use syntactically valid tax codes (`RSSMRA80A01H501U`, `VRDLGU75C41F205X`) that may belong to real people; prefer codes with a wrong check character. Edge cases worth documenting: a tax code that changes (late omocodia, corrections) creates a new person key; provisional numeric codes (11 digits) are rejected with `TAX_CODE_NOT_FOUND`.

### UCL-30 — Personal Telegram handle as support channel (Info)

The footer and notice link a personal Telegram account as "Assistenza". Consider a company channel to separate personal and service contacts.

## 5. What is done well

- **CIE verification:** explicit per-link chain validation with OpenSSL (`chain.js`) after finding that pkijs path building accepted an unsigned link; only pinned self-signed roots are anchors; certificates from the CMS are used only as intermediates; holder must not be a CA; key usage and policy checked; OCSP response signature verified explicitly, freshness checked, fail-closed.
- **Statement design:** ASCII, LF, deterministic; contains origin, chain id, contract, UP, mode, 32-byte nonce and expiry; rebuilt from the row and checked by hash; UP signature window and single-use state transitions with conditional `UPDATE … WHERE status = …`.
- **Privacy engineering:** tax code used once and dropped; HMAC with domain separation (`up-cie-link:person:v1:`); certificate reference AES-256-GCM encrypted with a version byte; error responses and logs carry codes only; tests assert that fake names/tax codes never appear in logs or responses; no cookies, no analytics.
- **Web security:** strict CSP without inline code, no third-party scripts, all network data inserted as text (`dom.js`), CORS limited to the public origin, `trust proxy` limited to loopback with nginx overwriting `X-Forwarded-For`, body size limits, parameterised SQL everywhere.
- **Contract:** small surface, soulbound (transfers, forced transfers, operators and batch calls blocked and tested), owner is a UP, emergency stop via `setAttester(0)`, holder can always `renounce()`; 25 tests.
- **Operations:** encrypted backups to an offline public key, integrity check, rotation, restore that never overwrites without `--force`; independent monitor; deployment records with commit hash; mainnet deploy guarded by `CONFIRM_MAINNET`; clean git history (no secrets, no `.p7m`/`.db`/`.env` ever committed).

## Appendix A — Proof-of-concept code

### A.1 Nonce gap after one reverted call (`backend/test/…`, Hardhat automine)

```js
import assert from "node:assert/strict";
import { after, before, describe, it } from "node:test";
import { ContractFactory, Wallet } from "ethers";
import { createMinter } from "../src/chain.js";
import { artifact, startNode } from "./helpers/hardhat-node.js";

describe("minter nonce gap", () => {
  let node, badgeAddress, up1, up2, attesterKey;
  before(async () => {
    node = await startNode();
    const [deployer] = node.wallets;
    attesterKey = node.keys[1];
    const upArt = artifact("universalProfile");
    const deployUp = async () => {
      const c = await new ContractFactory(upArt.abi, upArt.bytecode, deployer).deploy(Wallet.createRandom().address);
      await c.waitForDeployment();
      return c.getAddress();
    };
    const owner = await deployUp();
    up1 = await deployUp();
    up2 = await deployUp();
    const b = artifact("badge");
    const badge = await new ContractFactory(b.abi, b.bytecode, deployer).deploy(owner, new Wallet(attesterKey).address);
    await badge.waitForDeployment();
    badgeAddress = await badge.getAddress();
  });
  after(() => node?.stop());

  it("a reverted call must not break the following mints", async () => {
    const minter = createMinter(node.provider, badgeAddress, attesterKey);
    const exp = Math.floor(Date.now() / 1000) + 365 * 86400;
    await minter.attest(up1, exp, true);
    await assert.rejects(minter.invalidate(up2, "CERT_REVOKED")); // up2 has no valid badge: reverts
    await minter.attest(up2, exp, true); // today: "Nonce too high. Expected nonce to be 1 but got 2"
  });
});
```

### A.4 "UP-like" contracts (`contracts/contracts/test/AuditPoc.sol`)

```solidity
// SPDX-License-Identifier: Apache-2.0
pragma solidity 0.8.28;

interface IBadge { function renounce() external; }

/// Claims LSP0 + LSP1, accepts any ERC-1271 signature, renounces the badge while it is being minted.
contract AuditFakeUP {
    address public badge;
    constructor(address badge_) { badge = badge_; }
    function supportsInterface(bytes4 id) external pure returns (bool) {
        return id == 0x01ffc9a7 || id == 0x24871b3d || id == 0x6bb56a14;
    }
    function isValidSignature(bytes32, bytes memory) external pure returns (bytes4) { return 0x1626ba7e; }
    function universalReceiver(bytes32, bytes calldata) external payable returns (bytes memory) {
        if (msg.sender == badge) IBadge(badge).renounce();
        return "";
    }
}

/// Claims LSP0 and accepts any ERC-1271 signature, no LSP1: attest() always reverts (UCL-01 trigger).
contract AuditNoLsp1UP {
    function supportsInterface(bytes4 id) external pure returns (bool) { return id == 0x01ffc9a7 || id == 0x24871b3d; }
    function isValidSignature(bytes32, bytes memory) external pure returns (bytes4) { return 0x1626ba7e; }
}
```

Observed: both pass `createUpChecker().isUniversalProfile` and `isValidUpSignature` (any 65-byte signature); `AuditFakeUP` ends with status `Invalidated` while the transaction logs `Invalidated → Attested`; `AuditNoLsp1UP` makes `attest()` revert.

## Appendix B — Severity scale

- **Critical:** direct loss of funds/keys or mass exposure of personal data, exploitable now.
- **High:** core function broken or stoppable by an outsider, or serious integrity/privacy impact with a realistic path.
- **Medium:** significant weakness needing specific conditions, or a compliance gap that must be closed before real users.
- **Low:** hardening, defence in depth, limited impact.
- **Info:** documentation, hygiene, cosmetic.
